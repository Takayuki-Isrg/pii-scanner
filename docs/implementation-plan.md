## 1. 全体の順序

```
Phase 1（ルールベース）
  1-1 雛形 → 1-2 テスト基盤 → 1-3 列挙・読み取り → 1-4 ルール検出
  → 1-5 allowlist・集約 → 1-6 レポート・CLI → 1-7 評価・調整
        │
        ▼  Phase 1の完了条件を満たす
Phase 2（ローカルLLM）
  2-0 技術検証 → 2-1 方式の決定（ユーザー） → 2-2 LLM接続
  → 2-3 検出の統合 → 2-4 評価・調整

  2-0 の内訳（2026-11-20 時点）
    2-0a 事前調査 ............ 実施済み
    2-0b V1（argmax）......... 実施済み・暫定目標は未達
    2-0c V2（Viterbi）........ 実施済み・暫定目標は未達（改善なし）
    2-0d 次の検証 ............ 未決定（要件定義書 Q14）
```

Phase 2は、Phase 1の完了条件を満たしてから着手する。ただし2-0（技術検証）はPhase 1のコードに依存しないため、Phase 1と並行して進めてよい。

## 3. Phase 1（ルールベース）

### 3.1 モジュール構成

| モジュール | 責務 |
|---|---|
| `cli` | 引数の解析（対象フォルダ、出力先フォルダ、設定ファイル）、終了コードの決定 |
| `config` | 設定ファイルの読み込みと検証、初期値の保持 |
| `walker` | 対象ファイルの列挙。`.gitignore` と追跡状態の判定、リンクを辿らない制御 |
| `reader` | 読み取り専用でのファイルの読み込み、バイナリ判定、UTF-8の判定、行への分割 |
| `rules` | ルールの定義（ルールID、カテゴリ、パターン、除外条件、確信度、理由の定型文） |
| `rule_engine` | ルールの適用、エントロピーの計算、Luhnチェック、検出結果の生成 |
| `allowlist` | allowlistとの照合、「抑制済み」の印付け |
| `aggregator` | 重複の統合、ファイル単位のグループ化、並べ替え |
| `reporter` | テキストレポートの出力 |
| `models` | 検出結果、未検査の記録などのデータ構造 |

検出結果のデータ構造には検出値を持たせない。位置、カテゴリ、ルールID、確信度、理由だけを保持する（M1を構造で守る）。

### 3.2 手順

| # | 作業 | 内容 | 対応する要件 |
|---|---|---|---|
| 1-1 | 雛形 | パッケージの構成、`pyproject.toml`（Python 3.11.9以上、開発時の依存にpytest）、`models` | NFR-06、NFR-07 |
| 1-2 | テスト基盤 | テストコーパスを実行時に生成する仕組み、正解データ、必須条件のテスト（canaryが漏れない、対象ファイルが変わらない）。**検出ロジックより先に作る** | AC-01〜04 |
| 1-3 | 列挙・読み取り | `walker`、`reader`。未検査の記録 | FR-01〜14 |
| 1-4 | ルール検出 | `rules`、`rule_engine`。A群 → B群（B1、B2、B3、B6）→ E群の順に追加し、カテゴリごとに陽性・陰性のテストを通す | FR-20〜25 |
| 1-5 | allowlist・集約 | `allowlist`、`aggregator`、`config` | FR-50〜54、FR-70〜72 |
| 1-6 | レポート・CLI | `reporter`、`cli`、終了コード | FR-40〜43、FR-60〜65 |
| 1-7 | 評価・調整 | テストコーパスで再現率・適合率を計測する。サイズ上限、エントロピーのしきい値の初期値を決める。公開済みの自分のリポジトリで誤検出の件数と処理時間を実測する。READMEに使い方と制約事項を書く | D13、AC-30〜32 |

### 3.3 完了条件

次のすべてを満たしたとき、Phase 1を完了とする。

1. 必須条件の受入条件（AC-01〜04）の自動テストがすべて通る。
2. 機能の受入条件（AC-10〜20）の自動テストがすべて通る。
3. テストコーパスで、A群（認証情報）の再現率が100%である（AC-30）。
4. テストコーパスの陰性データが検出されない（AC-31）。
5. B群（B1、B2、B3、B6）とE群の再現率・適合率が、カテゴリごとに計測され記録されている（AC-32）。
6. サイズ上限、行長の上限、エントロピーのしきい値の初期値が決まり、設定ファイルから変更できる。
7. 実行時の依存が標準ライブラリだけである（Q2でGitコマンドを採る場合はGitを除く）。
8. 公開済みの自分のリポジトリ1つ以上でスキャンが最後まで完走し、処理時間が記録されている。
9. READMEに、使い方、設定、制約事項（Gitの履歴は対象外、氏名と住所はPhase 2で対応）が書かれている。

## 4. Phase 2（ローカルLLM）

### 4.1 手順

| # | 作業 | 内容 |
|---|---|---|
| 2-0 | 技術検証 | 合成データだけを使い、OPFでの日本語の氏名・住所の検出精度、検出位置、処理時間、GPUメモリ、ログへの混入の有無を確認する。本体のコードには組み込まない。2026-11-18の決定でV1を先に実施し、Ollamaでの読み込み（V0）は実施しないことになった。詳細は4.3節 |
| 2-1 | 方式の決定 | 2-0の結果をもとに、ユーザーがQ1を決める。追加する依存（NFR-08）と、LLMに渡す入力の範囲もここで確定する |
| 2-2 | LLM接続 | LLMに接続するモジュール。接続先がloopbackであることの検証。接続の失敗や不正な応答を「未検査（LLM）」として記録する処理。OPFを採用した場合はプロセス内での推論になるため、この手順の内容はQ1とQ16の決定後に見直す |
| 2-3 | 検出の統合 | LLMの検出結果（B4、B5）を検出結果に追加する。ルールの検出結果は削除・変更しない。レポートのヘッダにモデル名、検出項目に検出元 `llm` を出す |
| 2-4 | 評価・調整 | 同じテストコーパスで「ルールのみ」と「ルール＋LLM」を比較する。LLMに渡す前後の行数の初期値を決める。同じ入力を複数回実行し、結果のぶれを記録する |

### 4.2 完了条件

次のすべてを満たしたとき、Phase 2を完了とする。

1. Q1が決定され、要件定義書に反映されている。
2. Phase 1の完了条件1〜4を、LLM検出を有効にした状態でも満たす（canaryが漏れない、対象ファイルが変わらない、を含む）。
3. loopback以外の接続先を設定すると、スキャンを開始せずエラーで終了する（AC-05。見直しを検討中。要件定義書7.6節）。
4. LLM検出を無効にしたとき、Phase 1と同じレポートが出力される。
5. LLMに接続できない場合でも、ルールの検出結果が出力され、LLMで検査できなかったことがレポートに記録される（FR-33）。
6. LLMを有効にしても、ルールの検出結果が1件も減らない（FR-32）。
7. B4（住所）とB5（氏名）の再現率・適合率が計測され、「ルールのみ」との比較が記録されている。**OPF単体の評価とツール全体の評価は、分けて記録する。**
8. B4とB5の行単位の再現率が、それぞれ95%以上である（AC-33。暫定の開発目標であり、安全性を保証する基準ではない）。どの評価水準に適用するかなど、決まっていない点は要件定義書Q15。
9. LLM検出を有効にしたときの処理時間とGPUメモリが記録されている。
10. READMEに、モデルの入手方法、設定、制約事項が書かれている。

#### V2で比較した項目

すべてV1と同じテストデータ、同じ評価スクリプトで比較した。

1. 氏名・住所の行単位の再現率と適合率（しきい値は0.0、0.5、0.7、0.9）
2. 暫定目標（行単位の再現率95%以上）を満たすか
3. ひらがな・カタカナの氏名の見落とし件数と再現率
4. CSV内の氏名の見落とし件数と再現率
5. その他の表記別・ファイル形式別の見落とし件数
6. 陰性データでの誤検出の件数
7. 範囲の境界の一致（参考）
8. 3回の実行での再現性
9. 処理時間（Viterbi復号の時間を含む）とGPUメモリ
10. 推論中の通信の試行と、ログへの混入

結果は要件定義書7.5節にある。

#### 合格・未達の判断

要件定義書7.4節による。OPF単体の評価で、氏名・住所の行単位の再現率がそれぞれ95%以上なら「達成」、どちらかが下回れば「未達」とする。

V1・V2とも「未達」であり、計測したすべてのしきい値で未達だった。**2-0は完了扱いにしない。** 次の進め方は未決定（Q14）である。

#### 処理速度

- 原因の調査は後回しにする（2026-11-20の決定）。
- 計測は今後の検証でも続け、`metrics_<run>.json` に保存する。記録する項目は、モデルの読み込み時間、ファイルごとの処理時間、トークン数/秒、GPUメモリ（torch内の値とデバイス全体の値）である。

## 5. MVPの範囲外

次の項目は、Phase 1とPhase 2のどちらの完了条件にも含めない。

- IDの検出（マイナンバー、社員番号、学籍番号、会員ID、AWSアカウントID）。時期はQ9
- 電話番号の国際形式、海外の住所
- Gitの履歴のスキャン
- PDF、Office文書、画像、アーカイブ
- UTF-8以外の文字コード
- テキスト以外のレポート形式
- Gitフックとしての提供
