# PII・機密情報スキャンツール 要件定義書（MVP）

- 版: 2026-11-20 改訂（Phase 2技術検証の判断とV1・V2の結果を反映）
  - 2026-11-17: 未定事項 D1〜D15 の決定を反映
- 対象: Phase 1（ルールベース）と Phase 2（ローカルLLM）
- 実装計画は [implementation-plan.md](implementation-plan.md) を参照

表記のルール:

- **【確定】** ユーザーが決定した事項（D番号を併記）
- **【提案】** 設計上の提案。ユーザーの承認が必要
- **【要確認】** 仕様として決まっていない事項。11章に一覧がある

---

## 1. 目的と必須条件

GitHubに個人開発プロジェクトをプッシュする前に、ローカルフォルダをスキャンし、個人情報・認証情報が残っていないかをテキストレポートで確認する。

次の4点は必須条件であり、どのPhaseでも破ってはならない。

| # | 必須条件 |
|---|---|
| M1 | **検出値は完全にマスクする。** 値そのもの、値の一部、値のハッシュをレポートにもログにも出力しない |
| M2 | **スキャン対象ファイルを変更しない。** 内容、更新日時、属性のいずれも変えない |
| M3 | スキャン対象の内容を外部のAI APIに送信しない。LLMの接続先はローカル（loopback）に限る（後半の表現は見直しを検討中。7.6節） |
| M4 | 検出結果には、ファイル名、行番号、検出カテゴリ、検出理由を含める |

## 3. 検出対象

### 3.1 カテゴリ一覧

| 大分類 | カテゴリID | 対象 | 検出手段 | Phase |
|---|---|---|---|---|
| A. 認証情報 | `A1_PRIVATE_KEY` | 秘密鍵（PEM形式、OpenSSH形式） | ルール | 1 |
| | `A2_PROVIDER_TOKEN` | 形式が決まっているAPIキー・アクセストークン | ルール | 1 |
| | `A3_GENERIC_SECRET` | 汎用のSecret Key・トークン（キー名と値の組） | ルール＋エントロピー | 1 |
| | `A4_PASSWORD` | パスワード（代入、設定値、接続文字列） | ルール | 1 |
| | `A5_JWT` | JWT | ルール | 1 |
| B. 個人情報 | `B1_EMAIL` | メールアドレス | ルール | 1 |
| | `B2_PHONE` | 電話番号（日本の形式のみ。D15） | ルール | 1 |
| | `B3_BIRTHDATE` | 生年月日 | ルール（キーワードの近くの日付） | 1 |
| | `B4_ADDRESS` | 住所（日本の住所のみ。D15） | ローカルLLM | 2 |
| | `B5_PERSON_NAME` | 氏名 | ローカルLLM | 2 |
| | `B6_CARD_NUMBER` | クレジットカード番号（D11） | ルール（桁数＋Luhnチェック） | 1 |
| E. 環境情報 | `E1_USER_PATH` | OSユーザー名を含む絶対パス（D11） | ルール | 1 |
| | `E2_IP_ADDRESS` | IPアドレス（D11） | ルール | 1 |
| C. ID | `C1_ID` | マイナンバー、社員番号など | — | **MVP対象外**（D3） |

### 3.2 含める情報・含めない情報の境界

| カテゴリ | 含める | 含めない |
|---|---|---|
| 秘密鍵 | `-----BEGIN … PRIVATE KEY-----` のブロック | 公開鍵、証明書 |
| APIキー・トークン | 既知の形式に合う値 | プレースホルダ（`YOUR_API_KEY`、`xxxx`、`<token>`、`${API_KEY}`、`changeme` など） |
| 汎用Secret | キー名が secret / token / key / credential を含み、値の長さとエントロピーがしきい値以上のもの | 環境変数の参照、変数名だけのもの、ロックファイルなどのハッシュ値 |
| パスワード | リテラルの値、接続文字列に埋め込まれた値 | 空文字、プレースホルダ、入力処理のコード |
| メール | 下記以外のアドレス | RFC 2606/6761 の予約ドメイン（`example.com`、`*.test`、`*.invalid` など）。**noreply系のアドレス（D5）**。会社の公開連絡先（D5。判定方法は【要確認】Q5） |
| 電話番号 | 日本の固定電話・携帯電話の形式 | 国際形式（D15）、バージョン番号、日付、数字だけのID |
| 生年月日 | 「生年月日」「誕生日」「DOB」「birthday」などのキーワードの近くにある日付 | キーワードのない日付 |
| 住所 | 日本の住所で、都道府県＋市区町村＋番地レベルの記述 | 海外の住所（D15）、都道府県名や市名だけの記述 |
| 氏名 | 個人を指す氏名 | ライブラリ名、地名、一般名詞。本人が意図して公開する氏名はallowlistで抑制する（D4） |
| カード番号 | 桁数が合い、Luhnチェックを通る番号 | Luhnチェックを通らない数字列 |
| 絶対パス | OSユーザー名を含むパス（`C:\Users\<名前>\…`、`/home/<名前>/…`、`/Users/<名前>/…`） | ユーザー名を含まないパス、相対パス |
| IPアドレス | 範囲は【要確認】（Q6） | 範囲は【要確認】（Q6） |

以前の案にあった「社内やローカルのホスト名」は、D11の採用対象（絶対パス、IP、カード番号）に含まれていないため、MVPの対象外とする。

## 5. 機能要件

### 5.1 対象ファイルの列挙

| ID | 要件 |
|---|---|
| FR-01 | ユーザーが指定した1つのローカルフォルダを、再帰的にスキャンする |
| FR-02 | `.git/` ディレクトリはスキャンしない |
| FR-03 | 【確定 D12】`.gitignore` に記載されたファイルはスキャン対象外とする。ただしGitで追跡されているファイルは、`.gitignore` に記載されていてもスキャン対象とする |
| FR-04 | 【提案】Gitで追跡されておらず、`.gitignore` にも記載されていないファイルはスキャン対象とする（今後 `git add` されうるため） |
| FR-05 | シンボリックリンクとジャンクションは辿らない。対象フォルダの外にあるファイルは読まない |
| FR-06 | FR-03により対象外としたファイルの件数を、レポートのサマリに記載する |

FR-03の実現方法（Gitコマンドを呼び出すか、Gitリポジトリでないフォルダをどう扱うか）は【要確認】（Q2）。

### 5.2 ファイルの読み取り

| ID | 要件 |
|---|---|
| FR-10 | ファイルは読み取り専用で開く（M2） |
| FR-11 | 【確定 D7】UTF-8として読む。UTF-8として読めないファイルは「未検査」としてレポートに記録する |
| FR-12 | NULバイトを含むファイルはバイナリとみなし、「未検査」として記録する |
| FR-13 | 【確定 D13】サイズ上限を超えるファイル、長さの上限を超える行は検査せず（または上限までを検査し）、「未検査」として記録する |
| FR-14 | 対応形式はテキストファイルとする（ソースコード、設定ファイル、Markdown、テキスト、CSV、HTML、`.ipynb`、拡張子のないテキスト）。PDF、Office文書、画像、アーカイブはMVPの対象外とし、「未検査」として記録する |

【提案】BOM付きUTF-8はUTF-8として扱う。

### 5.3 ルールベース検出（Phase 1）

| ID | 要件 |
|---|---|
| FR-20 | 3.1節でPhase 1としたカテゴリを、ルールで検出する |
| FR-21 | 各ルールは、ルールID、カテゴリ、確信度（高・中・低）、検出理由の定型文を持つ |
| FR-22 | 3.2節の「含めない」条件に当たるものは検出しない |
| FR-23 | 1行に複数の検出がある場合、それぞれを別の検出結果とする |
| FR-24 | 複数行にまたがる検出（PEM形式の秘密鍵）は、開始行と終了行を記録する |
| FR-25 | 同じ箇所を複数のルールが検出した場合、1件にまとめる |

### 5.4 ローカルLLM検出（Phase 2）

| ID | 要件 |
|---|---|
| FR-30 | LLMを使う検出は、ユーザーが明示的に有効にしたときだけ実行する |
| FR-31 | LLMの接続先がloopback（`127.0.0.1`、`::1`、`localhost`）以外の場合、スキャンを開始せずエラーで終了する（M3）。**見直しを検討中**：Ollama（HTTP接続）専用の要件から、オフライン推論を基本とする要件へ変更する方向。正式な改訂は検証後に行う（7.6節） |
| FR-32 | LLMはルールの検出結果を削除・変更しない。検出結果の追加だけを行う |
| FR-33 | LLMに接続できない、応答が不正などの理由でLLM検出ができなかった箇所は、「未検査（LLM）」としてレポートに記録する。ルールの検出結果は通常どおり出力する |
| FR-34 | 使用したモデル名をレポートに記録する |

### 5.5 マスク

| ID | 要件 |
|---|---|
| FR-40 | 【確定 D6】レポートには検出値を一切出力しない。値の一部、ハッシュも出力しない（M1） |
| FR-41 | 検出値を含む行の本文も出力しない（氏名や住所は前後の文から推測できるため） |
| FR-42 | 【提案】検出値の長さ、列の終了位置も出力しない。出力するのは行番号と開始列だけとする（Q7） |
| FR-43 | 例外メッセージ、コンソール出力、ログにも、検査対象ファイルの内容を出力しない |

### 5.6 allowlist（誤検出の抑制）

| ID | 要件 |
|---|---|
| FR-50 | 【確定 D14】抑制条件は設定ファイルに記載する。検査対象ファイルには注釈コメントを追加しない |
| FR-51 | 【確定 D14】allowlistに一致した検出結果は削除せず、「抑制済み」としてレポートに区別して記載し、件数をサマリに記録する |
| FR-52 | 【確定 D4】本人が意図して公開する氏名・メールアドレスは、allowlistへの登録で抑制する |
| FR-53 | 【確定 D14】除外条件は必要最小限とする。【提案】各エントリは「ファイルパス」と「カテゴリまたはルールID」の両方を必須とし、全ファイル・全カテゴリを一括で抑制する指定は受け付けない |
| FR-54 | 各エントリには識別名を付け、レポートの「抑制済み」欄に、どのエントリで抑制したかを記載する |

allowlistの照合キー（値で照合するか）と、設定ファイルの置き場所・形式は【要確認】（Q3）。

### 5.7 レポート出力

| ID | 要件 |
|---|---|
| FR-60 | 【確定 D8】レポートは、ユーザーが指定したフォルダにテキストファイルとして出力する |
| FR-61 | レポートはファイル単位でまとめ、1つのファイルに複数の検出項目を表示する（6章） |
| FR-62 | 検出が0件の場合もレポートを出力する（サマリ、未検査、制約事項を含む） |
| FR-63 | 【提案】レポートのファイル名に実行日時を含め、既存のレポートを上書きしない |
| FR-64 | レポートに制約事項を必ず記載する（Gitの履歴は検査していない、未対応の形式がある、など） |
| FR-65 | 【提案】終了コードは 0（抑制されていない検出なし）、1（抑制されていない検出あり）、2（エラー）とする（Q8） |

### 5.8 設定

| ID | 要件 |
|---|---|
| FR-70 | 【確定 D13】サイズ上限、LLMに渡す前後の行数、エントロピーのしきい値は初期値を持ち、設定ファイルから変更できる |
| FR-71 | 設定ファイルがない場合は初期値で動作する |
| FR-72 | 設定ファイルの内容が不正な場合、スキャンを開始せずエラーで終了する |

初期値そのものは、Phase 1の評価で決める（D13）。

## 6. レポートの出力形式

### 6.1 構成

1. ヘッダ（実行日時、対象フォルダ、ツールのバージョン、LLMの使用有無とモデル名）
2. サマリ（ファイル数、カテゴリ別の検出件数、抑制済み件数、未検査件数）
3. 検出結果（ファイル単位）
4. 抑制済みの検出結果（ファイル単位）
5. 未検査の一覧
6. 制約事項

### 6.2 各検出項目に含める情報

| 項目 | 内容 |
|---|---|
| 行 | 行番号。複数行にまたがる場合は `12-39` の形式 |
| 列 | 検出の開始列 |
| カテゴリ | `A2_PROVIDER_TOKEN` など |
| ルールID | `R-A2-GITHUB-PAT` など。LLMの検出はLLM用のID |
| 確信度 | 高・中・低 |
| 検出元 | `rule` または `llm` |
| 理由 | 検出理由の文章。値を含めない |

並び順は、ファイルは相対パスの昇順、ファイル内は行番号・列の昇順とする。ファイルパスは対象フォルダからの相対パスで表示する。

【提案】ヘッダの「対象フォルダ」は末尾のフォルダ名だけを表示する。絶対パスにはOSユーザー名が含まれ、`E1_USER_PATH` で検出対象としている情報をレポート自身が出すことになるため。

----------------------------------------------------------------
 3. 抑制済みの検出結果（allowlistに一致）
----------------------------------------------------------------
[1] LICENSE    抑制済み 1件

  #1  行 3   列 20  B1_EMAIL  検出元: rule
      ルール   : R-B1-EMAIL
      allowlist: author-contact

----------------------------------------------------------------
 4. 未検査
----------------------------------------------------------------
  assets/logo.png        バイナリファイルのため検査していない

----------------------------------------------------------------

----------------------------------------------------------------
- Gitの履歴（過去のコミット）は検査していない。
- PDF、Office文書、画像、アーカイブは検査していない。
- 氏名と住所は、LLM検出が無効のため検査していない。

### 7.4 合格・未達の判断（R1。2026-11-20 決定）

**評価は2つの水準に分け、結果を混同しない。**

| 水準 | 対象 | 状態 |
|---|---|---|
| OPF単体の評価 | OPFの出力だけを、合成データの正解と照合する | V1・V2で実施した |
| ツール全体の評価 | 将来のルールベース検出とOPFの出力を合わせた、ツールとしての検出結果を照合する | 未実施（Phase 2の2-4で実施） |

**暫定の開発目標**

- 氏名（`private_person`）と住所（`private_address`）の**行単位の再現率が、それぞれ95%以上**であること。
- 検出漏れの少なさを重視するため、再現率を目標とする。
- これは暫定の開発目標であり、**安全性を保証する基準ではない**。

**判断の方法**

- 行単位の再現率は「正解の行（ファイルと行番号の組）のうち、同じラベルの検出がある行の割合」で計算する。
- 両方のラベルが95%以上なら「達成」、どちらかが95%未満なら「未達」とする。
- 次の事項は【要確認】（Q15）。
  - 判断に使うスコアのしきい値
  - 適合率の下限
  - ツール全体の評価にも同じ目標を適用するか
- V1・V2は、計測したすべてのしきい値（0.0〜0.9）で未達だった。したがって、これらの結論はしきい値の選び方に左右されない。

### 7.5 技術検証の結果（OPF単体の評価）

**条件（V1・V2で共通）**

| 項目 | 内容 |
|---|---|
| 環境 | Windows 11ネイティブ、Python 3.11.9、torch 2.11.0+cu128、transformers 5.23.0、RTX 5070（ドライバ610.88） |
| モデル | `openai/privacy-filter`、リビジョン `7ffa9a043d54d1be65afb281eddf0ffbe629385b`、bf16 |
| データ | 合成データ40ファイル（seed 20261118）。氏名100件、住所100件、陰性100件。CRLFのファイル10個、BOM付き8個 |
| 入力 | ファイル全体を一度に入力 |
| 実行 | GPUで各3回。3回の結果は、V1・V2ともに完全に一致した |

**V1とV2の違いは復号方式だけである。**

- V1：トークンごとにargmaxでラベルを決め、自前でBIOESを復号する。
- V2：V1と同じモデル出力に、公式 `opf` の `ViterbiCRFDecoder`（コミット `f7f00ca7fb869683eb732c010299d901457f19c3`）を変更せずに適用する。
- V2では、`opf` の実行環境一式（独自のモデル実装、tiktoken、triton）は使っていない。そのため、`opf` 一式で動かした場合と結果が一致するかは未検証である。

**結果：行単位（しきい値0.0。検出したスパンをすべて採用）**

| 指標 | V1 氏名 | V2 氏名 | V1 住所 | V2 住所 |
|---|---|---|---|---|
| 再現率 | 0.720 | 0.700 | 0.856 | 0.827 |
| 適合率 | 0.947 | 0.959 | 0.824 | 0.852 |
| 見落とした行の数 | 28 | 30 | 15 | 18 |
| 目標（再現率95%以上） | 未達 | 未達 | 未達 | 未達 |

しきい値0.9では、V1は氏名0.640・住所0.779、V2は氏名0.630・住所0.740だった（再現率）。

**氏名の見落とし（表記・ファイル形式別。しきい値0.0）**

| 区分 | 件数 | V1 見落とし（再現率） | V2 見落とし（再現率） |
|---|---|---|---|
| ひらがな | 14 | 10（0.286） | 10（0.286） |
| カタカナ | 14 | 7（0.500） | 8（0.429） |
| CSV内の氏名 | 12 | 10（0.167） | 10（0.167） |
| 漢字（姓と名の間に空白なし） | 19 | 6（0.684） | 6（0.684） |
| 漢字（空白あり） | 39 | 5（0.872） | 6（0.846） |
| ローマ字 | 14 | 0（1.000） | 0（1.000） |

**結論：Viterbi復号（V2）では、再現率は改善しなかった。**

- 氏名・住所とも、再現率はわずかに下がった。
- ひらがな・カタカナの氏名とCSV内の氏名の見落としは、減らなかった。
- 適合率はわずかに上がり、陰性データでの誤検出は10件から9件に減った。

**その他の結果**

| 項目 | V1 | V2 |
|---|---|---|
| 検出位置 | 空白を除いた完全一致では、行番号の誤りは0件。CRLFとBOMによる行のずれもなかった | 同左 |
| 範囲の境界 | 先頭の空白を含む、敬称・郵便番号を含む、などのずれがある | 空白を除いた完全一致の再現率は、氏名0.44→0.49、住所0.52→0.54と小さく改善した |

**結果の限界**

- データは自作の定型文から作った小規模な合成データであり、実際のコードやドキュメントでの精度は分からない。
- 範囲の完全一致の値は、正解データ側の決め方（敬称や郵便番号を範囲に含めない）に影響される。そのため、判断には行単位の値を使う。

### 7.6 接続要件（FR-31・AC-05）の見直しについて

- 検証した方式は、プロセス内で推論し、ネットワークを使わない。そのため、loopbackへの接続を前提とするFR-31・AC-05は、そのままでは当てはまらない。
- 見直しは「オフライン推論を基本とする要件」の方向で検討する。正式な改訂は検証後に行う。
- 改訂案の具体的な内容（モデルの自動ダウンロードを禁止するか、通信の有無をどう確認するか）は【要確認】（Q16）。
- 検証では、ネットワーク監視をPython側の処理だけに対して行った。C言語で書かれた拡張機能の内部の通信は、この方法では検知できない。
